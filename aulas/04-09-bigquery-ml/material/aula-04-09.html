2Silver: o JSON vira tabelamão na massa

Duas funções resolvem 90% de qualquer JSON: uma para campo, uma para lista.

Passo 1 — pegar um campo

JSON_VALUE
SELECT
  id_anuncio,
  JSON_VALUE(listing, '$.address.city')          AS cidade,
  JSON_VALUE(listing, '$.address.neighborhood')  AS bairro,
  JSON_VALUE(listing, '$.usableAreas[0]')        AS area_util
FROM `SEU_PROJETO.SEU_DATASET.imoveis_bronze`
LIMIT 10;

O $ é a raiz do documento. O ponto desce um nível. O [0] pega o primeiro item quando o campo é uma lista.

Passo 2 — quando o campo é uma lista de objetos

Este é o conceito que trava todo mundo. O campo pricingInfos não é um valor: é uma lista, porque o mesmo anúncio pode estar à venda e para alugar. Você precisa dizer qual dos dois quer.

JSON_QUERY_ARRAY + UNNEST — o pulo do gato
SELECT
  id_anuncio,
  (SELECT JSON_VALUE(p, '$.price')
   FROM UNNEST(JSON_QUERY_ARRAY(listing, '$.pricingInfos')) AS p
   WHERE JSON_VALUE(p, '$.businessType') = 'SALE'
   LIMIT 1) AS preco_venda
FROM `SEU_PROJETO.SEU_DATASET.imoveis_bronze`
LIMIT 10;
FunçãoServe paraDevolve
JSON_VALUEum campo simplesSTRING (ou NULL)
JSON_QUERY_ARRAYabrir uma listaARRAY de JSON
UNNESTvirar a lista em linhasuma linha por item
SAFE_CASTconverter tipo sem quebraro valor ou NULL
SAFE_CAST, sempre. CAST derruba a query inteira se achar um valor torto. SAFE_CAST devolve NULL e segue. Em dado bruto, use o seguro.

Passo 3 — construir a Silver

O script completo está em silver_01_json.sql. Ele monta 25 colunas de uma vez. Aqui está o formato, para você entender o desenho:

silver_01_json.sql (trecho)
CREATE OR REPLACE TABLE `SEU_PROJETO.SEU_DATASET.imoveis_silver` AS
SELECT
  id_anuncio,
  SAFE_CAST(
    (SELECT JSON_VALUE(p, '$.price')
     FROM UNNEST(JSON_QUERY_ARRAY(listing, '$.pricingInfos')) AS p
     WHERE JSON_VALUE(p, '$.businessType') = 'SALE'
     LIMIT 1) AS FLOAT64)                        AS preco,
  SAFE_CAST(JSON_VALUE(listing,'$.usableAreas[0]') AS FLOAT64) AS area_util,
  SAFE_CAST(JSON_VALUE(listing,'$.bedrooms[0]')   AS INT64)   AS quartos,
  JSON_VALUE(listing, '$.address.neighborhood')              AS bairro,
  JSON_VALUE(listing, '$.unitTypes[0]')                       AS tipo_imovel,
  ARRAY_LENGTH(JSON_QUERY_ARRAY(listing,'$.amenities'))     AS qtd_comodidades
  -- ... e mais 19 colunas
FROM `SEU_PROJETO.SEU_DATASET.imoveis_bronze`;
Aquela parede de 14 mil caracteres virou uma tabela de 25 colunas. Foi um comando. Só que ela ainda está mentindo pra gente.

3O dado está mentindomão na massa

Nenhum modelo vai te avisar que o número é impossível. Quem sabe disso é você.

A tabela está pronta. Quem quer treinar o modelo agora?

Defeito 1 — a média não bate com a mediana

estatística descritiva
SELECT
  COUNT(*)                                        AS anuncios,
  ROUND(AVG(preco))                              AS media,
  ROUND(APPROX_QUANTILES(preco, 2)[OFFSET(1)])   AS mediana,
  ROUND(STDDEV(preco))                           AS desvio_padrao,
  ROUND(MAX(preco))                              AS maximo
FROM `SEU_PROJETO.SEU_DATASET.imoveis_silver`
WHERE preco IS NOT NULL;

A média dá mais que o dobro da mediana. Quando isso acontece, alguma coisa do lado direito está puxando tudo. Vá ver quem é:

quem está puxando
SELECT id_anuncio, tipo_imovel, bairro, area_util, ROUND(preco) AS preco
FROM `SEU_PROJETO.SEU_DATASET.imoveis_silver`
WHERE preco > 50000000
ORDER BY preco DESC
LIMIT 20;
O que você vai encontrar
  • Um lote de 681 m² anunciado por R$ 1,4 bilhão
  • Uma fazenda por R$ 675 milhões
  • Um apartamento de 74 m², no Vila Rosa, por R$ 499 milhões

Alguns são erro de escala — o anunciante digitou o valor em centavos, ou repetiu zeros. Outros são imóvel caro de verdade: este dataset é genuinamente de alto padrão (mediana em torno de R$ 9 milhões). Distinguir os dois casos é o trabalho.

Agora meça o estrago. Não estime, meça:

o número que importa
SELECT
  COUNTIF(preco > 50000000)                                  AS suspeitos,
  COUNT(*)                                                  AS total,
  ROUND(100 * COUNTIF(preco > 50000000) / COUNT(*), 1)      AS pct,
  ROUND(STDDEV(preco))                                     AS desvio_com_eles,
  ROUND(STDDEV(IF(preco <= 50000000, preco, NULL)))       AS desvio_sem_eles
FROM `SEU_PROJETO.SEU_DATASET.imoveis_silver`
WHERE preco IS NOT NULL;
2,9% das linhas controlam 90% da variação.

Defeito 2 — a unidade trocada

áreas impossíveis
SELECT id_anuncio, tipo_imovel, bairro, area_util, ROUND(preco) AS preco
FROM `SEU_PROJETO.SEU_DATASET.imoveis_silver`
WHERE area_util > 10000
ORDER BY area_util DESC
LIMIT 15;
O campeão

Uma fazenda com usableAreas = 390.000.000 m². Isso é 390 km² — mais da metade do município de Goiânia (~729 km²). Um imóvel à venda ocupando metade da cidade.

Quase certamente alguém digitou a área em m² num campo que o sistema esperava em hectares, ou colou o valor errado. O BigQuery aceitou sem piscar — é um número válido.

A lição. Validade de tipo não é validade de significado. 390000000 é um FLOAT64 perfeitamente correto. Só um humano que sabe o tamanho de uma fazenda percebe o problema.

Defeito 3 — informação repetida no texto

o preço escrito na descrição
SELECT
  COUNTIF(REGEXP_CONTAINS(descricao, r'R\$'))                 AS com_preco_no_texto,
  COUNT(*)                                                     AS total,
  ROUND(100 * COUNTIF(REGEXP_CONTAINS(descricao, r'R\$')) / COUNT(*), 1) AS pct
FROM `SEU_PROJETO.SEU_DATASET.imoveis_silver`
WHERE descricao IS NOT NULL;

Cerca de 23% dos anúncios trazem o valor escrito dentro da descrição. Guarde esse número. Ele volta na etapa 6, e não vai ser do jeito que você espera.

A camada Gold

Cada linha do WHERE abaixo é uma decisão que você toma e justifica, não uma regra que veio de fora:

silver_02_etl.sql — a Gold
CREATE OR REPLACE TABLE `SEU_PROJETO.SEU_DATASET.imoveis_gold` AS
SELECT
  id_anuncio, preco, area_util, quartos, banheiros, suites, vagas,
  condominio, iptu_anual, bairro, tipo_imovel, uso, imobiliaria,
  qtd_comodidades, descricao,
  ROUND(preco / area_util, 2) AS preco_por_m2
FROM `SEU_PROJETO.SEU_DATASET.imoveis_silver`
WHERE preco IS NOT NULL
  AND preco     BETWEEN 50000 AND 50000000  -- corta erro de escala (2,9%)
  AND area_util BETWEEN 20    AND 10000     -- corta unidade trocada
  AND cidade = 'Goiania';                    -- 999 de 1000 sao daqui
Isso que você acabou de fazer tem nome: ETL.
Não é a parte chata antes do ML. É a parte que decide se o ML vai servir pra alguma coisa.
Desafios
  1. Em vez de cortar em R$ 50 mi, use o método do IQR (APPROX_QUANTILES(preco, 4), corte acima de Q3 + 1,5×IQR). Quantos anúncios sobram? Qual critério você defenderia numa reunião?
  2. Os anúncios com erro de escala se concentram em alguma imobiliária? Se sim, o problema é do dado ou de quem cadastra?
  3. Quantas linhas a Gold perdeu em relação à Silver, e em porcentagem? Sempre meça isso — perder 60% dos dados numa limpeza é motivo para revisar as regras.

4O cardápio do BigQuery ML

Primeiro a pergunta. Depois o model_type. Nunca o contrário.

Sua perguntaNome dissomodel_type
Quanto vai ser? (um número)regressãoLINEAR_REG, BOOSTED_TREE_REGRESSOR
É A ou B?classificaçãoLOGISTIC_REG, BOOSTED_TREE_CLASSIFIER
Quanto no mês que vem?série temporalARIMA_PLUS
Quais se parecem entre si?agrupamentoKMEANS
O que recomendar?recomendaçãoMATRIX_FACTORIZATION

Já tenho um modelo prontoimportarTENSORFLOW, ONNX, REMOTE
Por que ARIMA_PLUS não é demonstrado hoje. O campo de data deste dataset é a data de publicação do anúncio, não a data de venda. Não existe série temporal aqui. O dado decide o modelo — não o contrário. Querer usar ARIMA num dado sem série é o erro que mais aparece em trabalho de disciplina.

O que não cabe no BigQuery ML: visão computacional, arquitetura customizada, treino distribuído em GPU. Isso é Vertex AI, e é a aula de 02/10.

5Regressão: quanto vale este imóvel?mão na massa

Você já sabe CREATE TABLE. É o mesmo verbo.

ml_03_regressao.sql — treinar
CREATE OR REPLACE MODEL `SEU_PROJETO.SEU_DATASET.modelo_preco`
OPTIONS (
  model_type            = 'LINEAR_REG',
  input_label_cols      = ['preco'],   -- <<< o que queremos prever
  data_split_method     = 'AUTO_SPLIT',
  enable_global_explain = TRUE
) AS
SELECT
  preco,            -- label
  area_util, quartos, banheiros, suites, vagas, qtd_comodidades,
  bairro, tipo_imovel, uso
FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold`;

Três coisas para reparar enquanto o treino roda:

  1. Não existe lista de features. input_label_cols diz qual coluna é a resposta; todo o resto do SELECT vira entrada.
  2. bairro e tipo_imovel são texto e entraram direto. Em Python isso seria OneHotEncoder + ColumnTransformer. Aqui você só colocou a coluna.
  3. AUTO_SPLIT. O BigQuery separou treino e validação sozinho. Você não escreveu, e não tem como esquecer de fazer.
avaliar
SELECT * FROM ML.EVALUATE(MODEL `SEU_PROJETO.SEU_DATASET.modelo_preco`);
MétricaO que é
mean_absolute_errorEm reais: quanto o modelo erra, em média
r2_scoreDe 0 a 1: quanto da variação do preço ele conseguiu explicar. 0 = chutar a média
R² não é nota de prova. É quanto do mundo o modelo enxergou. Preço de imóvel é difícil: um R² entre 0,4 e 0,7 é um resultado honesto, e dá uma discussão muito melhor do que 0,99. Se der 0,99, desconfie — e vá para a etapa 6.
prever — ordenado pelos PIORES erros, de propósito
SELECT
  bairro, tipo_imovel, area_util, quartos,
  ROUND(preco)                   AS preco_real,
  ROUND(predicted_preco)         AS preco_previsto,
  ROUND(predicted_preco - preco) AS erro
FROM ML.PREDICT(
  MODEL `SEU_PROJETO.SEU_DATASET.modelo_preco`,
  (SELECT * FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold`)
)
ORDER BY ABS(predicted_preco - preco) DESC
LIMIT 20;

Olhe os 20 piores erros. O que eles têm em comum?

Quase sempre há um padrão: são os mais caros, ou de um bairro com poucos anúncios, ou de um tipo raro. Isso é análise de erro — e é mais útil que o R².

perguntar ao modelo o que ele achou importante
SELECT * FROM ML.GLOBAL_EXPLAIN(MODEL `SEU_PROJETO.SEU_DATASET.modelo_preco`)
ORDER BY attribution DESC;
O modelo não é uma caixa preta por natureza.
Ele é uma caixa preta quando você não pergunta.
Desafios
  1. Troque LINEAR_REG por BOOSTED_TREE_REGRESSOR e compare. Ganhou quem teve o melhor R², ou quem teve o menor erro em reais?
  2. Adicione preco_por_m2 como feature. O R² vai para perto de 1. Por que isso é um problema e não uma vitória? (dica: preco_por_m2 = preco / area_util)
  3. Treine só com imóveis RESIDENTIAL. Melhorou? O que isso diz sobre misturar residencial e comercial no mesmo modelo?

6Classificação: residencial ou comercial?mão na massa

Muda uma palavra dentro do OPTIONS. Mais nada.

Antes de treinar: conte as classes

a linha de corte
SELECT

Se eu criar um modelo que responde RESIDENTIAL para tudo, sem olhar nada, qual vai ser a acurácia dele?

Anote o número antes de continuar. Ele é a nota mínima. Um modelo que não bate isso não aprendeu nada — mesmo com 80% de acerto.

ml_04_classificacao.sql — treinar
CREATE OR REPLACE MODEL `SEU_PROJETO.SEU_DATASET.modelo_uso`
OPTIONS (
  model_type         = 'LOGISTIC_REG',   -- <<< a unica mudanca estrutural
  input_label_cols   = ['uso'],
  data_split_method  = 'AUTO_SPLIT',
  auto_class_weights = TRUE,             -- compensa o desbalanceamento
  enable_global_explain = TRUE
) AS
SELECT
  uso,
  area_util, quartos, banheiros, suites, vagas, qtd_comodidades,
  preco, preco_por_m2, bairro, tipo_imovel
FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold`
WHERE uso IS NOT NULL;
auto_class_weights. Sem isso, o modelo descobre que chutar a classe majoritária já acerta a maioria e nunca se esforça para achar a minoritária. Classe desbalanceada não é detalhe estatístico — é o modelo percebendo que dá pra colar na prova.
avaliar e ler a matriz de confusão
SELECT * FROM ML.EVALUATE(MODEL `SEU_PROJETO.SEU_DATASET.modelo_uso`);

SELECT * FROM ML.CONFUSION_MATRIX(MODEL `SEU_PROJETO.SEU_DATASET.modelo_uso`);
MétricaResponde
accuracy% de acertos — compare com a linha de corte que você anotou
recallDos comerciais que existiam, quantos ele achou?
precisionDos que ele chamou de comercial, quantos eram mesmo?
Precision e recall respondem perguntas diferentes.
Escolher qual importa não é decisão do modelo. É sua.

Filtro de spam: precision importa mais (não jogue e-mail bom fora). Exame de câncer: recall importa mais (não deixe doente passar).

os erros cometidos com MAIS confiança
SELECT
  bairro, tipo_imovel, area_util,
  uso           AS uso_real,
  predicted_uso AS uso_previsto,
  ROUND((SELECT MAX(p.prob) FROM UNNEST(predicted_uso_probs) AS p), 3) AS confianca
FROM ML.PREDICT(
  MODEL `SEU_PROJETO.SEU_DATASET.modelo_uso`,
  (SELECT * FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold` WHERE uso IS NOT NULL)
)
WHERE uso <> predicted_uso
ORDER BY confianca DESC
LIMIT 20;

Repare no predicted_uso_probs: classificação não devolve só o rótulo, devolve a probabilidade de cada classe — num array de struct. É o mesmo UNNEST do JSON, no começo da aula.

Um modelo errando com 51% de certeza está em dúvida.
Errando com 98% de certeza, ele aprendeu a coisa errada. São problemas diferentes.
Desafios
  1. Treine de novo sem tipo_imovel. A acurácia cai quanto? Esse segundo modelo é pior — ou é mais honesto?
  2. Rode com auto_class_weights = FALSE e compare a matriz de confusão. Onde exatamente ele passou a errar?
  3. Troque por BOOSTED_TREE_CLASSIFIER. Valeu o custo de treino a mais?

7O modelo bom demaisacompanhe na tela

Métrica quase perfeita em problema do mundo real é quase sempre vazamento — não genialidade.

Os modelos erraram bastante. Vamos melhorar. Temos uma coluna que nem usamos ainda: a descrição do anúncio. Texto é informação.

Passo 1 — extrair informação do texto

É o que qualquer pipeline de NLP faria: puxar entidades do texto livre. Números com R$ na frente são a entidade mais óbvia que existe.

ml_05_armadilha.sql — a feature nova
CREATE OR REPLACE TABLE `SEU_PROJETO.SEU_DATASET.imoveis_gold_texto` AS
SELECT
  *,
  SAFE_CAST(
    REPLACE(REPLACE(
      REGEXP_EXTRACT(descricao, r'R\$\s*([0-9][0-9\.]*(?:,[0-9]{2})?)'),
    '.', ''), ',', '.') AS FLOAT64
  ) AS valor_citado_no_texto
FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold`;

Passo 2 — treinar de novo, com ela

o modelo v2
CREATE OR REPLACE MODEL `SEU_PROJETO.SEU_DATASET.modelo_preco_v2`
OPTIONS (
  model_type            = 'LINEAR_REG',
  input_label_cols      = ['preco'],

O v2 ganha. E ganha muito.

Publicamos esse modelo?

Antes de responder: de onde saiu o número que a gente extraiu?

A resposta
as duas colunas lado a lado
SELECT
  id_anuncio,
  ROUND(preco)                 AS preco_da_coluna,
  ROUND(valor_citado_no_texto) AS valor_extraido_do_texto,
  SUBSTR(descricao, 1, 120)    AS trecho
FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold_texto`
WHERE valor_citado_no_texto IS NOT NULL
ORDER BY ABS(valor_citado_no_texto - preco) ASC
LIMIT 15;

As duas colunas de número são iguais.

Você não criou uma feature. Você copiou a resposta de dentro do texto e colou na entrada do modelo.
O modelo não ficou melhor. Ele ficou com a prova na mão.

Isso tem nome: vazamento de alvo (data leakage).

A prova de que o modelo não serve

Uma métrica global esconde o crime. Basta separar em dois grupos:

decompondo o erro
SELECT
  IF(valor_citado_no_texto IS NOT NULL,
     'anuncio com preco escrito no texto',
     'anuncio SEM preco no texto')            AS grupo,
  COUNT(*)                                    AS anuncios,
  ROUND(AVG(ABS(predicted_preco - preco)))   AS erro_medio_em_reais
FROM ML.PREDICT(
  MODEL `SEU_PROJETO.SEU_DATASET.modelo_preco_v2`,
  (SELECT * FROM `SEU_PROJETO.SEU_DATASET.imoveis_gold_texto`)
)
GROUP BY grupo;
O que aparece
  • Nos ~23% que têm o preço no texto: erro próximo de zero
  • Nos ~77% restantes: erro enorme
Esse modelo não avalia imóvel. Ele lê anúncio.
Em produção, todo imóvel novo chega sem preço — se tivesse preço, você não precisaria do modelo.

E dá para descobrir isso com uma query só: ML.GLOBAL_EXPLAIN vai mostrar valor_citado_no_texto dominando todo o resto. A explicabilidade não é enfeite de slide — é teste de sanidade.

O checklist — leve este da aula

Antes de acreditar em qualquer métrica boa, três perguntas:

  1. Essa coluna vai existir no momento em que eu for prever?
    O preço no texto não existe num imóvel que ainda não tem preço.
  2. Essa coluna foi preenchida depois de acontecer o que eu quero prever?
    Data de pagamento para prever inadimplência. Data de alta para prever internação. Status do pedido para prever cancelamento.
  3. O resultado ficou bom demais?
    Métrica quase perfeita é quase sempre vazamento.
Treinar modelo no BigQuery é uma linha de SQL.
O trabalho de verdade é tudo que veio antes do CREATE MODEL: abrir o JSON, achar a fazenda do tamanho de metade de Goiânia, e desconfiar do modelo que acertou demais.
Isso nenhuma ferramenta faz por você.
